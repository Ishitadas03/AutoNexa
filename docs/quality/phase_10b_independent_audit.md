## 4. Pareto Correctness Findings

### 4.1 Mixed Maximize/Minimize Objectives
- **Mathematical Implementation:** In `pareto.py`, each objective specifies `direction: "maximize"` or `"minimize"`. In `check_dominance`:
  ```python
  dir_mult = 1.0 if obj.direction == "maximize" else -1.0
  utility_a = dir_mult * val_a
  utility_b = dir_mult * val_b
  ```
  This projects all metrics into unified scalar utility where higher is always better.
- **Verification:** Verified mathematically and tested under combinations of:
  - Maximize score + Minimize latency + Minimize size + Minimize complexity.
  - Minimize RMSE + Minimize latency + Minimize size + Minimize complexity.

### 4.2 Floating-Point Tolerance
- **Tolerance Constant:** `FLOAT_TOLERANCE = 1e-7`.
- **Condition for Weak Dominance:** $u_a \ge u_b - \epsilon$.
- **Condition for Strict Superiority:** $\exists j, u_{a,j} > u_{b,j} + \epsilon$.
- **Finding:** Verified. Prevents catastrophic cancellation and rounding noise in floating-point latency or normalized scores from asserting non-existent dominance.

### 4.3 Equal Candidates and Duplicates
- If candidate $A$ and candidate $B$ have identical measurements across all evaluated objectives, neither candidate has $u_{A,j} > u_{B,j} + \epsilon$. Consequently:
  - $A \not\succ B$ and $B \not\succ A$.
  - Neither dominates the other; both remain in the Pareto frontier.
  - In `select_model`, ties within $\pm \epsilon$ are tracked in `tied_candidate_ids` and surfaced in `selection_explanation`.

### 4.4 Feasible vs Infeasible Candidates
- Resource constraints ($\text{max latency}$, $\text{max size}$, $\text{max training time}$, $\text{min performance}$, $\text{max complexity}$) are evaluated strictly before Pareto frontier construction.
- Infeasible candidates are recorded with detailed violation structures (`ConstraintViolation`), but are **strictly excluded** from the Pareto frontier $\mathcal{P}$.
- Pairwise dominance is evaluated strictly among candidates in the feasible set $\mathcal{F}$.

### 4.5 Normalization & Utopia Point Distance under Changing Ranges
- Normalized utility on objective $k$ is mapped to $[0, 1]$ across feasible models:
  - Maximize: $\hat{u}_k = \frac{f_k - \min f_k}{\max f_k - \min f_k}$
  - Minimize: $\hat{u}_k = \frac{\max f_k - f_k}{\max f_k - \min f_k}$
- **Constant Objectives:** If $\max f_k - \min f_k \le 10^{-7}$ (e.g. all candidates share identical complexity or single candidate), $\hat{u}_k = 1.0$. This yields $(1.0 - \hat{u}_k)^2 = 0$, meaning constant columns contribute zero penalty and do not distort candidate rankings across varying dimensions.
- **Missing Objectives:** Prior to the audit fix, missing objectives defaulted to $0.0$, which penalized models with unmeasured metrics. Following the audit fix, missing objectives are omitted from `normalized_scores`, and Utopia distance is calculated strictly over valid measured objectives:
  $$D_{\text{utopia}} = \sqrt{\frac{\sum_{k \in \text{valid}} w_k (1.0 - \hat{u}_k)^2}{\sum_{k \in \text{valid}} w_k}}$$

## 5. Resource Measurement Findings

### 5.1 Inference Latency & Warm-Up Protocol
- **Warm-Up Execution:** Before timing, `ResourceProfiler.profile_inference_latency` executes a preliminary forward inference pass on the input batch. This warms CPU branch predictors, populates NumPy memory pools, and initializes C extensions.
- **Repeated Timing:** Measures $R = 5$ repeated inference passes over a batch of up to 100 samples using `time.perf_counter()`. Latency per individual sample is computed as $\frac{T_{\text{elapsed}}}{N_{\text{samples}} \cdot R} \cdot 1000$ and rounded to 4 decimal places ($0.1\,\mu\text{s}$ resolution).

### 5.2 Separation of Profiling Overhead from Training
- In `multi_objective_service.py`, training duration timing (`t0 = time.perf_counter()`) starts immediately before `candidate_pipeline.fit(X_train_val, y_train_val)` and stops immediately after.
- Cross-validation evaluation occurs prior to full training; latency benchmarking, disk serialization, and complexity extraction occur strictly *after* training timing has completed.
- Training duration is cleanly isolated from profiling overhead.

### 5.3 Characterization of Memory Profiling (`tracemalloc`)
- **Audit Clarification:** `tracemalloc` tracks memory allocations within the Python heap. It does **not** track memory allocated directly by native C/C++ extensions (such as OpenBLAS, MKL, or OpenMP worker threads).
- The schema documentation (`CandidateMeasurement.peak_memory_bytes`), platform metadata, and methodology disclaimer have been updated to explicitly state:
  > *"Peak memory allocated during training in bytes on the Python heap via tracemalloc (excludes external native C/C++ library buffers)."*

### 5.4 Estimator-Specific Structural Complexity
- Complexity is extracted based on estimator class architecture rather than arbitrary weights:
  - **Random Forest:** Total nodes across ensemble trees ($\sum \text{node\_count}$), max depth, leaf count, tree count.
  - **Decision Tree:** Single tree node count, leaf count, max depth.
  - **HistGradientBoosting:** Effective capacity ($\text{n\_iter} \times \text{max\_leaf\_nodes}$).
  - **Linear Models (LogisticRegression, Ridge):** Number of non-zero feature coefficients ($\sum [\beta_j \neq 0]$) and total parameters including intercept.
- Every complexity score specifies a clear unit (`tree_nodes`, `effective_nodes`, `nonzero_coefficients`, or `tunable_hyperparameters`).

## 6. Leakage and Evaluation Findings

### 6.1 Holdout Partition Isolation
- The raw input dataset is partitioned immediately upon ingestion:
  ```python
  X_train_val, X_test, y_train_val, y_test = train_test_split(..., test_size=0.2, random_state=42)
  ```
- **Zero Leakage Verified:**
  - Fold cross-validation operates strictly on $(X_{\text{train\_val}}, y_{\text{train\_val}})$.
  - `ColumnTransformer` (scaling, imputation, one-hot encoding) is instantiated freshly and fitted inside each cross-validation fold.
  - Candidate operational profiling uses $X_{\text{train\_val}}$.
  - Pareto dominance and model selection evaluate cross-validation generalization and operational costs.
  - $(X_{\text{test}}, y_{\text{test}})$ is evaluated **only after** candidate selection has completed.

### 6.2 Dynamic Re-Selection Holdout Integrity
- During dynamic re-selection via `POST /api/v1/benchmarks/multi-objective/{id}/select`, if a new candidate is selected, its holdout metrics are evaluated against the cached untouched test partition $(X_{\text{test}}, y_{\text{test}})$ without retraining or touching training data.
- Verified via regression test `test_select_model_dynamic_constraints`.

## 10. Remaining Limitations

1. **Memory Profiler Scope:** `tracemalloc` measures Python heap allocations only. High-capacity libraries utilizing external C++/Fortran allocations (such as BLAS or multithreaded OpenMP buffers) are not captured in `peak_memory_bytes`.
2. **Benchmark Dataset Scale:** The reference research datasets contain $N=200$ rows. On multi-million-row enterprise datasets, training duration and memory footprints will scale non-linearly.
3. **Cross-Family Structural Complexity:** While AutoNexa provides family-specific units, directly equating 50 decision tree nodes to 50 linear coefficients remains an approximation; users should prioritize latency and artifact size for cross-family deployment comparisons.
4. **Single-Node Execution:** Profiling assumes execution on a single local worker. Multi-node distributed training clusters (e.g., Ray or Dask) would require distributed timing synchronization.
